# E2E Test Plan — sftp-relay

**STATUS: BUILT AND GREEN (2026-09-05).** All five increments shipped; 19 tests pass,
three consecutive clean runs (`docker compose down -v` between each). Everything below
is kept as the record of what was built and why. Deviations from the original plan are
marked "as built".

Read first: `CLAUDE.md` (architecture), `definition_of_done.md` §2 (the scenario list
this plan implements), `plan_to_implement.md` Phase 10 (what is still outstanding).

---

## Why this is buildable

The Pi/NAS split is nothing but SSH. Both halves are reproducible in containers, so the
whole topology fits in one compose file:

| Real | Stand-in | Notes |
|---|---|---|
| Remote SFTP server | `sftp-source` container | openssh sftp, seeded fixture tree |
| Synology NAS | `fake-nas` container | sshd + `lftp` + `sshpass`, destination volume |
| Raspberry Pi | `relay` container | the real image, built from this repo |

The existing Go tests spin up an **in-process** ssh server (`internal/sftpclient/sftpclient_test.go:31`,
`startServer`). That is a unit-test fixture, not this. Do not try to reuse it — E2E
drives the shipped container image through a browser.

## Layout to create

```
test/e2e/
  docker-compose.yml        the three services + fixture volumes
  fake-nas/Dockerfile       alpine + openssh-server + lftp + sshpass
  fake-nas/entrypoint.sh    host key gen, authorized_keys, sshd -D
  fixtures/seed.sh          generates the source tree (incl. the 200 MB file)
  keys/                     generated at setup time, gitignored
  package.json              @playwright/test only — keep web/ deps clean
  playwright.config.ts      baseURL http://localhost:8088, retries 0, trace on failure
  global-setup.ts           wait for health, configure settings, add the servers
  helpers.ts                nas() exec helper, checksum(), queue(), waitForJob()
  specs/*.spec.ts           one file per scenario group
```

`test/e2e/node_modules`, `test/e2e/keys` and any generated fixture blobs go in
`.gitignore`. The 200 MB file is **generated, never committed**.

## The stack

### `sftp-source`

Use `atmoz/sftp` — an openssh sftp server with chroot-per-user that takes both password
and public-key auth, which the suite needs (the `sshpass` path vs. the key path).
Two users: `keyuser` (public key) and `passuser` (password), same mounted tree.

Fixture tree, per the DoD, generated by `fixtures/seed.sh` into a named volume:

```
/upload/small.txt               a few KB, known content
/upload/big.bin                 200 MB from /dev/urandom
/upload/empty.bin               0 bytes
/upload/name with spaces ü.txt  spaces + non-ASCII
/upload/tree/a/b/c/deep.txt     three levels, for the breadcrumb scenario
/upload/tree/...                ~5 more files for the mirror + multi-select scenarios
```

Record `sha256` of every fixture at seed time into `/upload/SHA256SUMS`; the transfer
specs compare against that rather than recomputing on both ends.

### `fake-nas`

Alpine + `openssh-server`, `lftp`, `sshpass`, `coreutils`. A `nas` user with the relay's
public key in `authorized_keys`, a writable destination volume, and — this matters —
**`lftp` deliberately placed outside the non-interactive `PATH`** (symlink it into
`/opt/bin`, keep it off the login PATH) so the startup probe at `internal/nas/nas.go:454`
is actually exercised rather than trivially satisfied.

Destination root: `/volume1/media`, matching the Synology shape. Set
`allowed_dest_roots=/volume1/media`.

**Known gap, state it in the spec comments:** the real Synology chroots its SFTP
subsystem to the share root, which is exactly what `nas.ShellPath` exists to paper over.
The fake NAS does not chroot, so `ShellPath` resolves to identity and that path stays
untested by E2E. It has unit coverage, and real-NAS behaviour remains a manual item.
Adding a chrooted `Subsystem sftp` that maps `/volume1/*` to `/*` is a worthwhile later
increment, not a blocker.

### `relay`

Built from `deploy/Dockerfile` with `TARGETARCH=amd64` (CI runners are x86). Env:
`AUTH_USER=e2e`, `AUTH_PASS=e2e-pass`, `NAS_SSH_KEY_PATH=/keys/nas_key`, `LOG_LEVEL=debug`.
Published on `localhost:8088`, as `deploy/docker-compose.yml` already does. `/data` is a
**named volume** — the restart-resume scenario needs the DB to survive
`docker compose restart relay`, and the cleanup scenario needs it torn down between runs.

### Configuration, not DB surgery

`global-setup.ts` configures the app through its own API with basic auth — never by
writing SQLite directly:

1. Poll `GET /api/health` until 200 (cap ~60 s).
2. `PUT /api/settings`: `nas_host=fake-nas`, `nas_user=nas`, `nas_port=22`,
   `nas_tmp=/volume1/media/.tmp`, `allowed_dest_roots=/volume1/media`, `concurrency=2`,
   `segments=4`, `parallel=2`. Leave `lftp_path` **empty** so the startup probe fills it
   in — that probe is under test.
3. `POST /api/servers` for both `keyuser` and `passuser`.
4. `POST /api/servers/{id}/test` once each, which is what pins the remote host key
   (trust-on-first-connect). `nas_host_key` pins on the first NAS operation.

Everything after that is browser-driven. No spec may touch the DB.

## Scenarios

DoD §2 verbatim, grouped into spec files. Each box is one `test()`.

### `auth.spec.ts`
- [x] Unauthenticated request rejected (401); correct credentials grant access

### `servers.spec.ts`
- [x] Server CRUD — add, test the connection, edit, delete

### `browse.spec.ts`
- [x] Browse three levels deep and back via breadcrumb; sizes and modified dates render;
      directories sort first
- [x] Destination browse — navigate the NAS tree, create a folder, and confirm a path
      outside `allowed_dest_roots` is rejected with a visible error

### `transfer.spec.ts`
- [x] Single file download — progress advances, reaches 100%, checksum matches on the
      fake-NAS volume
- [x] Directory download — recursive mirror, full tree with matching checksums and
      correct nesting
- [x] Multi-select batch — five items, queued in one action, all complete

### `lifecycle.spec.ts`
- [x] Concurrency — queue more than `concurrency`; only N run, the rest show a queue
      position
- [x] Cancel — mid-transfer; the job reports cancelled, no `lftp` process remains, the
      temp workspace is gone
- [x] Resume after restart — restart the relay container mid-flight; the job is
      `interrupted` and **resumes** with partial bytes retained, not from zero
- [x] Failure surfacing — a nonexistent remote path fails with a readable error, visible
      in the UI, with retry offered
- [x] Unreachable NAS — `docker compose stop fake-nas` mid-job gives a clear error rather
      than a hang, and the app recovers when it comes back

### `resilience.spec.ts`
- [x] SSE — kill the stream; the client reconnects with backoff, resyncs from the
      snapshot, and shows the disconnected indicator meanwhile
- [x] Multi-client — two browser contexts see identical live progress
- [x] Mobile viewport — the full browse-to-queue flow at 375px, no horizontal scroll, no
      overlapping controls

### `cleanup.spec.ts` (runs last)
- [x] Zero orphaned temp workspaces (`$NAS_TMP/job-*`, `/tmp/sftp-relay-job-*`), zero
      orphaned `lftp` processes, zero leaked SSH connections on the fake-NAS

## Increments

Ship in this order; each one leaves the suite green. All five are done.

**A — stack up.** compose file, both Dockerfiles, seed script, playwright config,
global-setup, `auth.spec.ts`, `servers.spec.ts`, `browse.spec.ts`.
Exit: `docker compose up` then `npx playwright test` passes locally.

**B — the point of the whole thing.** `transfer.spec.ts`.
Exit: `big.bin` arrives on the fake-NAS volume with a matching sha256, and the progress
bar was observed to move before it did.

**C — lifecycle.** `lifecycle.spec.ts`. Expect this to be the increment that finds real
bugs — cancel and restart-resume are where the races live.

**D — resilience.** `resilience.spec.ts`, `cleanup.spec.ts`.

**E — CI.** Wire it into `.github/workflows/ci.yml` and prove three consecutive green runs.

## CI wiring

A third job in `.github/workflows/ci.yml`, gated on `go` and `web` passing:

```yaml
  e2e:
    needs: [go, web]
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: test/e2e
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: docker compose up -d --build
      - run: npx playwright test
      - if: failure()
        run: docker compose logs --no-color > relay-logs.txt
      - if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: e2e-artifacts
          path: |
            test/e2e/test-results/
            test/e2e/relay-logs.txt
```

Chromium only. The DoD's browser matrix is a manual concern; three browsers in CI buys
flake, not coverage.

## Rules for whoever builds this

- **`retries: 0`.** A flaky test here is a real race in the job system, and quarantine is
  explicitly not an option (DoD §2). If a test flakes, the bug is in `internal/jobs`
  until proven otherwise.
- **No `waitForTimeout` as synchronisation.** Poll `GET /api/jobs/{id}` or await a UI
  state. Sleeps are how this suite rots.
- **Assert on the NAS filesystem, not just the UI.** A job row saying `done` is not
  evidence a file arrived. Every transfer scenario ends in a `sha256sum` inside
  `fake-nas`.
- **Fixture generation is a build step, not a commit.** `git status` must be clean after
  a full run.
- One `docker compose down -v` between runs; the resume and cleanup specs are stateful.

## Gotchas already known

- `docker compose restart relay` must not lose `/data` — use a named volume, not a bind
  mount into a temp dir the runner wipes.
- The 200 MB fixture must be big enough that a transfer outlives the restart and cancel
  scenarios on a fast CI runner. If it completes too quickly, throttle those specs with
  `segments=1` rather than growing the file.
- lftp writes the in-flight file as `.in.<name>` (`xfer:use-temp-file yes`), so a
  mid-transfer filesystem assertion must look there, not at the final name.
- The relay pins host keys on first connect. `docker compose down -v` discards the DB, so
  the pins are re-established by `global-setup`; regenerating the fake-NAS host key
  *without* dropping the volume will look like an attack, correctly.
- Password-auth transfers need `sshpass` on the fake-NAS. Leaving it out is a legitimate
  extra scenario (assert the `opkg install sshpass` remediation surfaces), but it is not
  one of the mandatory boxes.
- nginx buffering: the SSE assertions only mean anything through the container's nginx on
  `:8088`. Never point Playwright at the Go port directly.

## As built — deviations from the plan above

Everything else landed as written. These five points did not:

- **Key distribution.** A `keygen` init service generates `nas_key`, `remote_key` and a
  persistent `nas_hostkey` into the bind-mounted `./keys`, and every other service waits
  on it (`service_completed_successfully`). Only *directories* are bind-mounted from
  there: compose creates a missing bind source as a directory, and all containers are
  created before keygen runs, so mounting `./keys/nas_key` as a file would have handed
  the relay an empty folder. `global-setup.ts` reads `keys/remote_key` from the host to
  POST it to `/api/servers`.

- **The port is configurable.** `E2E_PORT` (default 8088) in both the compose file and
  the Playwright config, so the suite can run beside a dev stack already on 8088.

- **`global-setup` restarts the relay once.** The container boots before the NAS is
  configured, so the startup tool probe skips itself. One restart after `PUT
  /api/settings` runs the real boot path — pinning `nas_host_key`, sweeping stale
  workspaces, resolving lftp off the non-interactive `PATH` — and fails setup loudly
  instead of failing inside the first transfer spec.

- **Throttling is an lftp shim, not `segments=1`.** Two containers on a loopback move
  200 MB in under a second, which leaves the progress, cancel, restart-resume and
  multi-client scenarios nothing in flight to observe; `segments=1` does not change
  that. `tc` was tried first and is not an option — Docker Desktop's kernel ships no
  `act_police` module. `fake-nas/lftp-wrapper.sh` sits in front of the real binary and
  prepends `set net:limit-total-rate` when `/tmp/e2e-throttle` exists; with no such file
  it is `exec` plus argv and nothing else. `throttle()` / `unthrottle()` in `helpers.ts`
  drive it.

- **Two extra scenarios beyond the DoD list.** `transfer.spec.ts` also covers the
  zero-byte file and the spaces-and-unicode filename, because the fixtures exist and the
  assertions are three lines. `lifecycle.spec.ts`'s unreachable-NAS test finishes by
  restarting the relay and asserting the boot sweep clears the workspace a `docker stop`
  SIGKILLed past the cleanup trap — which is the DoD §4 SIGKILL case.

- **Cancel leaves the queue screen.** A cancelled job is terminal, so its card moves to
  History rather than turning grey in place. That cost an hour of chasing a phantom
  cancellation bug; the assertion now follows the row to `#history`.

- **Six UI test hooks were added.** `data-testid` on the job card (with `data-job-id`,
  `data-status`, `data-percent`), the server row, the two browse panes, the selection
  bar and the SSE indicator. Nothing else in the app changed for the suite's benefit.
